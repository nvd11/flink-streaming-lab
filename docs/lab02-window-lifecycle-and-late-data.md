# Lab 02 深度设计规格：窗口生命周期与迟到三部曲

## 1. 实验背景与业务痛点
真实金融场景中，退款（REFUND）与冲正交易常常在数分钟乃至数小时后才送达。如果窗口仅仅在 Watermark 到达时“一刀切”彻底关闭并丢弃迟到数据，会导致账目永久性失衡（平账失败）。
为此，Flink 提供了**迟到治理的三道防线**：
1. **第一道防线**：`WatermarkStrategy.forBoundedOutOfOrderness(T)`（在事件源头留出乱序缓冲缓冲带）；
2. **第二道防线**：`allowedLateness(T_late)`（窗口在首次触发后**不销毁状态**，迟到数据进入时重新触发计算并输出修正值）；
3. **第三道防线**：`sideOutputLateData(OutputTag)`（超过 `allowedLateness` 彻底超期的迟到数据，重定向至侧输出流做审计落盘）。

## 2. 状态机与窗口触发推演
设滚动窗口为 10 秒：$[10:00:00, 10:00:10)$
- 乱序容忍度：2 秒 (`forBoundedOutOfOrderness(2s)`)
- 允许迟到度：5 秒 (`allowedLateness(5s)`)
- 侧输出标签：`OutputTag<FinancialTxEvent> LATE_TAG`

### 时钟生命周期时间线
```text
Event Time:    10:00:00 -------------- 10:00:10 ----- 10:00:12 --------- 10:00:17 ---->
Window [0, 10): |<--- 正常接收数据区间 --->|
Watermark:                                         到达 10:00:10 (由于 2s 乱序，由 10:00:12 触发)
                                                   首次触发 Fire: 输出首次净支出统计
                                                   |<-- 5s allowedLateness 保护期 -->|
                                                                                    Watermark 到达 10:00:15
                                                                                    (由 10:00:17 触发)
                                                                                    窗口状态彻底清除 Clean
                                                                                    此后到达的数据落入 SideOutput
```

## 3. 实验验证目标与断言
1. **首次触发断言**：当输入数据推进 Watermark 至窗口结束时间（10:00:10）时，窗口如期触发，输出第一次聚合结果。
2. **二次修正触发断言**：在 `[10:00:10, 10:00:15)` 期间到达属于该窗口的数据，验证该窗口再次触发（Accumulate & Retract / Update），下游收到包含新增金额的修正结果。
3. **侧输出兜底断言**：当 Watermark 超过 10:00:15 后，到达属于该窗口的数据不再触发窗口计算，而是 100% 被捕获至侧输出流，主流无重复输出。
